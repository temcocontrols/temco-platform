# Temco Learn — the published site

**What it is.** The website readers open: `https://temcocontrols.github.io/temco-learn/`. Static and read-only — no authoring, no drafts, no editing. A project's documentation is written in [Temco Platform](../temco-platform/README.md); this repository serves the result.

**How it relates.** One direction only: the platform builds a project and imports that build here; nothing is ever written back to a project's sources.

```text
Temco Platform      pages → build → Add a Build → Make the Downloads → Publish
Temco Learn         catalog → guard → build → deploy
```

| Step | Who does it | What it leaves behind |
|---|---|---|
| a project's pages | the platform | `dist/site` inside the project folder |
| **Add This Build to the Site** | the platform, in this clone | `public/imported/<id>/<version>/` and `content/<id>/site.json` |
| **Make the Downloads** | the platform, in this clone | `public/pdf/<id>/<version>.pdf`, `public/chm/…`, `public/download/manifest.json` |
| **Publish** | the platform, in this clone | one commit and a push to `main` |
| `catalog` → `guard` → `build:fast` | this repository's CI | `public/catalog.json` it then deploys as `dist/` |

The full path, from an empty folder to a live page, is [getting-started.md](../temco-platform/getting-started.md). It is its own repository (`temcocontrols/temco-learn`), cloned to `~/temco/temco-learn` unless `temcoLearn.siteRepo` says otherwise — the application is a client of that checkout, not its owner.

## Stack

| Choice | Is |
|---|---|
| Vite, React 19, Fluent UI v9 | one single-page app; the routes live in the fragment (`#/<project>/<version>/<page>`) because GitHub Pages serves static files and cannot rewrite a path |
| Markdown **and** imported HTML | both become rows of one catalog, so a project can be written here or built elsewhere |
| `catalog`, `search`, `pdf`, `chm`, `zip` scripts | everything derived is generated by a script; nothing is hand-maintained |
| Playwright | prints the PDFs; `hhc.exe` compiles the Windows help file |

## Layout

```text
temco-learn/
├── content/
│   ├── config.json                 site-wide answers: repository, edit branch, hints
│   ├── sections.json               the categories: documentation, training, tests, products, qa, topics
│   └── <id>/site.json              one project: title, section, summary
├── public/
│   ├── imported/<id>/<version>/    pages a project's own build wrote
│   ├── pdf/<id>/<version>.pdf      the whole-guide PDF — committed, not generated by CI
│   ├── chm/<id>/<version>.chm      the help file — committed, not generated by CI
│   ├── download/manifest.json      what the download menu offers
│   ├── content/                    catalog rows — generated
│   └── catalog.json, search.json   what the app reads — generated
├── scripts/                        catalog · search · pdf · chm · zip · check-content · check-artifacts
├── src/                            the app
└── .github/workflows/              pages.yml · release.yml
```

`public/catalog.json` is the one file the app reads to know what exists. Every row is either a **Markdown page** this repository authors, or an **imported page** a project's build wrote; the app does not care which until it renders one.

## How content arrives

1. A project builds its documentation — `dist/site`, or `dist/docs` when its own generator wrote it.
2. **Add This Build to the Site** copies it to `public/imported/<id>/<version>/` and writes `content/<id>/site.json`. The project's id is its folder's name; its section defaults to `documentation`.
3. `npm run catalog` turns both kinds of page into one version in one reading order, and rewrites `public/catalog.json`, `public/content/` and the download bundles.
4. `npm run pdf` prints the PDFs and mirrors them into `public/pdf/`; `npm run chm` compiles the help files and writes `public/download/manifest.json`.

Committing the imports is deliberate: reviewable, free to host, and simple to roll back. The whole path, from an empty folder to a live page, is [getting-started.md](../temco-platform/getting-started.md).

## What the deploy does

| Workflow | Trigger | Steps |
|---|---|---|
| `pages.yml` | a push to `main` | `npm ci` · `npm run check` · `npm run build:fast` (`VITE_BASE=/temco-learn/`) · `npm run guard` · upload `dist` · deploy to Pages |
| `release.yml` | a `v*` tag matching `package.json` | `check` · `guard` · `build:fast` · pack the whole site as a zip |

`guard` (`scripts/check-artifacts.mts`) fails the deploy when a catalogued version has no committed PDF, or when the manifest promises a `.chm` that is not on disk. CI never builds those files: a Linux runner has neither the fonts nor `hhc.exe`.

Locally: `npm run build:fast`, then `npm run serve -- --port 1025`.

## Not here

- No authoring, drafts, review or editing — that is Temco Platform's work.
- No second copy of a project's sources: what arrives is the build, not the repository.
- Nothing is ever written back to a project's repository.
